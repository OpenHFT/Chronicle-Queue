== Findings and disposition

The alias hazard and performance regression are both real. The original three
evidence tests are retained. Executing them locally reproduces 20,001 header
reads for a 20,000-record `HUGE_DAILY_XSPARSE` tail lookup, 545 reads for
`HUGE_DAILY` above 16 MiB, and an incorrect physical record returned by
`moveToIndex()` with a stale aliased tracker. The corresponding base reads
2 headers for either tail lookup and has the same pre-existing `moveToIndex()`
defect.

The write regression is not limited to alternating appenders. The ordinary
`writingDocument()` path calls `prepareAndReturnWriteContext()` ->
`resetPosition()` -> `lastSequenceNumber()` before opening the document,
including with one appender. Separate controls reproduce 20,004 header reads
for a single-appender document write and 20,005 for an alternating-appender
write on the reviewed head. Both controls pass their bounded-work assertions
on the original base.

Separate real-file regressions now reproduce the finite-position shortcut
and forward `toEnd()` failures on both the reviewed head and original base.
These are pre-existing defects, not regressions introduced by this PR.
The `linearScanByPosition0()` tracker shortcut applies when a finite requested
position equals the published address. It does not override the indexed
starting point of an ordinary `Long.MAX_VALUE` lookup.

== Retained implementation

The live codec's alias-period bound and stable full-position rereads remain.
The same checks now guard the previously unprotected index, finite-position
and forward-end shortcuts. The public forward-end path falls back to indexed
recovery when the tracker pair cannot be proved.

Repeated lookups can instead use a full position/sequence pair established by
a committed write or by a successful scan from an independently known starting
point. That pair belongs to one physical `MappedFile` and one thread. It is never constructed
by treating a wrapped tracker result as trustworthy. A lookup scans forward
from that immutable committed record, including any newly committed suffix.
An earlier finite lookup does not discard a newer verified pair.

This adds no file-format change, cross-process publication protocol,
per-write allocation after initialization, or synchronization on the write
path. A thread-local weak-key map lets stores reuse the pair while the same mapping
remains live. It uses object identity rather than a pathname or cycle number,
so replacing a cycle file does not inherit a previous mapping's pair. The cache
does not reserve or retain mapped files. Nearby tailer scans may supply full
queue indices; a cycle-relative sequence may only replace a starting index
within the scan's bounds.
The guarantee depends on committed queue records retaining their physical
positions and sequence order; arbitrary external rewriting of committed
records is outside that invariant.

The retained `//!` comments associate each release-code decision with a
discriminating test. These mappings are a review aid, not a substitute for the
publication invariant. A mutation that removes an incidental scanner read
should not become a failure merely because a test asserts an exact collaborator
call count.

=== Cost boundary

A warmed tail lookup scans records committed since its verified pair instead of
rescanning the entire sparse-index interval. Single-appender and alternating
`writingDocument()` calls, direct byte writes followed by a tail lookup, and
repeated reader/index lookups and public `excerptsInCycle()` queries have
deterministic bounded-work regressions.
Those bounds apply to the controlled workload; an arbitrarily large intervening
write burst can still require scanning its newly committed records.

`excerptsInCycle()` releases its store in a `finally` block on every invocation.
When the same mapping remains live, the replacement store now reuses the proved
pair. A new mapping or thread with no verified pair still needs indexed recovery
above the codec's alias period. The cache does not transfer proof between
threads or processes. This update must not be described as eliminating every
tail scan or completing issue
https://github.com/OpenHFT/Chronicle-Queue/issues/1704[#1704]. That issue's separate
scan-source counters and concurrent stress acceptance criteria remain open.

== Rejected constant-time proofs

Neither proposed shortcut establishes an exact pair:

* Probing only `lastWritePos - period` misses an older data record two or more
  periods behind. The probed offset can be inside its payload.
* Even one period behind, metadata can separate consecutive data records.
  The previous data record need not end at the newly published position.
* A 30-bit limit on an individual physical record does not bound the total
  distance between data publications. Metadata, structural records and padding
  must also be included, as must supported recovery/publication paths.

`SequenceAliasGapTest` uses actual queue files and the production codec with
one- and two-period gaps, with and without intervening metadata. Both
publication directions and both inclusive modes are covered. An independently mapped reader
also checks the stale-tracker case without a previously verified pair.
The proposed one-period header probe is executed as a mutation and is rejected
by these tests. No 4 GiB Queue integration reproduction is claimed for the
record-size exemption: it remains an unproved design candidate, and is not
implemented.

== Evidence tests

`SCQIndexingReviewEvidenceTest` retains the three original cases and adds
single-appender, alternating-appender, finite-position and forward-end controls,
plus direct-byte-write, warmed-reader/index, repeated public count and
replacement-file coverage. Sequence correctness
is asserted before work bounds, and the alias reader tests check the physical
record or position, not just a successful return code.

`SequenceAliasGeometryTest` adds deterministic writer-advance interleavings for
the three newly guarded shortcuts, including a capture below the alias period
followed by publication above it. These hooks control when a real write occurs;
they do not script a codec answer.

== Benchmark methodology

`LastSequenceNumberJLBHBenchmark` supports `-Dappenders=1` and `2`. The write
interval and the `excerptsInCycle()` interval have independent timestamps;
both samples are recorded after both timed regions. Each invocation appends a
record, and the harness prints actual population, last sequence, sparse-index
anchor and distance from that anchor before warmup and after every run.

`-Dpath` now identifies an existing parent directory for a newly created,
uniquely named child. Cleanup deletes only that owned child. The validation
runs leave a sentinel queue file in the supplied parent and check that its
contents survive and the owned child is removed.

Fresh comparison runs use the same corrected benchmark on the exact base and
reviewed production revisions above. They use one 65,536-byte filler plus
10,000 small records, 100 warmup writes, three runs of 500 writes at 500/s,
and coordinated omission disabled. Population is 10,001 before warmup,
10,101 before run 1, then 10,601, 11,101 and 11,601 after runs 1-3. The sparse
anchor remains sequence 0. These are growing workloads, not steady-state
10,000-record queues.

Raw outputs, exact JVM options, hardware/filesystem details and reproduction
commands accompany this report in link:pr-1706-evidence/README.adoc[the evidence directory]. The comparison is from
one developer machine, not an isolated performance lab. Deterministic header
counts are the acceptance gate; timings provide context.

Median latency in microseconds, shown as run 2 / run 3; run 1 is excluded
by the JLBH configuration. Host: AMD Ryzen 9 5950X, Linux x86_64, ext4,
OpenJDK 21.0.12, `-XX:ActiveProcessorCount=4` (full options in raw output).

== Decision log

The review branch was integrated without rewriting its history. The report's
single-appender explanation, timing, directory handling, measurement provenance
and proposed proofs were corrected before being used as an implementation
brief. Mutation survivors identified two missing controls: direct byte writes
without assertion-driven scans, and a warmed reader's indexed lookup. Those
controls now justify the relevant optimizations. Scan bookkeeping is retained
once per completed scan rather than performed through a thread-local lookup
for every header. Extending reuse across store releases exposed that nearby
seeks pass full queue indices; the existing random-seek regression now also
justifies the bound that keeps those separate from cycle-relative sequences.

Recommend updating `TRACKER_PUBLICATION_REVIEW.md`
(`/prompts:TRACKER_PUBLICATION_REVIEW`) and the corresponding AGENTS notes to
require metadata/multiple-period gaps, both publication directions, cold versus
warmed stores, single-appender controls, assertion-disabled production-path
controls, safe benchmark-owned directories, exact-revision raw measurements,
and clean compilation after mutation restoration.
