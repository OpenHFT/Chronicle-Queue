= Roll File Cleanup
:toc:
:toclevels: 3
:css-signature: demo

`RollFileCleanupMain` removes old Chronicle Queue roll files using the persisted positions of named tailers.

This is different from checking which files are currently open. A process can be down, but its named tailer can still have unread data. This tool treats the named tailer index as the durable contract: if a named tailer has not read past a roll file, that roll file is retained.

== When to use it

Use this tool when a queue directory grows because one or more named consumers have stopped, fallen behind, or been retired.

Typical cases:

* a gateway was stopped for a long time and still pins old roll files;
* a consumer was replaced but its named tailer entry remains in the table store;
* a production queue needs an offline retention sweep that is safer than deleting by age;
* free disk is becoming more important than preserving the unread backlog of a dead consumer.

Do not use this as a substitute for understanding the queue. The tool is deliberately conservative until you ask it to delete or park.

== How it decides what is removable

For each queue, the tool calculates two floors:

. the newest `N` roll-cycle numbers are always retained (`--keep N`);
. any named tailer positioned before that floor pulls the delete floor back to its own cycle.

A roll file is removable only when it is below the effective delete floor.

The keep window is by roll-cycle number, not by count of files on disk. This matters for sparse queues. For example, with hourly rolling and a queue idle for a day, many roll-cycle numbers may have no file. In that case, `--keep 48` means keep the last 48 hourly cycle numbers, not necessarily 48 files.

An index of `0` is treated as parked or never-read, so it does not pin any roll file.

[WARNING]
====
A named tailer that has just been registered but has not yet read also sits at index `0`, and is therefore indistinguishable from a parked one. Do not run with `--delete` while bootstrapping a new from-start consumer: its intended backlog is not protected and may be removed before it first reads.
====

[#sizing-keep]
=== Sizing `--keep` for late-arriving tailers

`--delete` runs against a live queue, so `--keep N` is a safety decision, not only a disk one.

The sweep reads named-tailer positions once, then deletes. A consumer that registers - or first reads - *after* that snapshot is not yet pinning anything, so a roll it still needs can be removed just before, or just as, it arrives. It might see a roll that is about to be removed, or miss a roll that was removed moments before it looked.

Only named tailers have a persisted position, so only they pull the delete floor down. An un-named (anonymous) tailer records nothing, is invisible to the sweep, and pins no rolls - so for any reader that consumes without a name, `--keep N` is the *only* retention control. Everything such a reader might still need must fall within the last `N` cycles, because nothing else protects it.

Choose `N` for the latest a reader could turn up, not for how many recent files you want to keep. The question is "how far back must any future reader still be able to start?". If consumers can appear hours later, restart after an outage, or replay from an old position, then `N` - counted in roll-cycle numbers - must span that whole window, with margin. The default of `2` is a conservative floor, not a recommendation: set it deliberately from your worst-case arrival and replay time.

[#reserved-ids]
=== Reserved named-tailer ids

Named tailer ids ending in `.lock` or `.version` are rejected by `createTailer(String)`.

A named tailer `a` keeps its state in the queue metadata under three keys: `index.a` (its committed position), `index.a.lock` and `index.a.version` (its lock and replication-version metadata). A tailer *named* `a.lock` or `a.version` would store its own position under `index.a.lock` or `index.a.version` - the very keys tailer `a` uses - so the two tailers would silently share and corrupt each other's state, and tools reading tailer positions could not tell a real tailer from another tailer's metadata. The suffixes are therefore reserved.

== Running the tool

From the `Chronicle-Queue` project root:

[source,bash]
----
mvn exec:java@RollFileCleanup -Dexec.args="/var/queues --keep 48 --min-free 20G --verbose"
----

or directly by main class:

[source,bash]
----
mvn exec:java \
  -Dexec.mainClass="net.openhft.chronicle.queue.main.RollFileCleanupMain" \
  -Dexec.args="/var/queues --keep 48 --min-free 20G --verbose"
----

The root can be a queue directory, or a directory whose immediate children are queue directories. A root that does not exist (or is not a directory) is an error (exit code `2`). Directories inside a queue directory are not supported: if a discovered queue contains a nested queue directory - usually the sign of a stray roll file copied into the parent, which makes the parent itself look like a queue and hides the real queues below it - the sweep warns.

A queue that fails to open or analyse (for example, corrupt metadata) is warned about and skipped; the remaining queues are still swept, so one bad queue never stops retention for the rest of the root.

== Running periodically with cron

For a host-level periodic sweep that starts again after a reboot, run the tool from `cron` rather
than keeping the Java process alive with `--interval`. For example, to run every hour at five
minutes past the hour:

[source,bash]
----
# /etc/cron.d/chronicle-roll-file-cleanup
SHELL=/bin/bash
PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin

5 * * * * chronicle cd /opt/Chronicle-Queue && mvn -q exec:java@RollFileCleanup -Dexec.args="/var/queues --keep 48 --min-free 20G --delete --fail-on-warn" >> /var/log/chronicle-roll-file-cleanup.log 2>&1
----

This form runs a single sweep each time cron starts it. After a machine restart, the system cron
daemon resumes the schedule without needing a long-running clean-up JVM. Use an absolute project
path, run as the user that owns the queue files, and redirect output to a log file that is rotated.

Two operational notes:

* Invoking through Maven means the cron host needs the project checked out with its dependencies already resolved. For a leaner deployment, run the packaged application directly, for example
+
[source,bash]
----
java -cp "chronicle-queue-all.jar" net.openhft.chronicle.queue.main.RollFileCleanupMain \
  /var/queues --keep 48 --min-free 20G --delete --fail-on-warn
----
* With `mvn -q` and default logging, only warnings reach the log. A successful sweep is silent unless you enable debug logging (see <<Logging and exit behaviour>>). This is usually what you want for cron: quiet on success, loud on a warning, non-zero exit under `--fail-on-warn`.

== Options

[cols="1,1,4", options="header"]
|===
| Option
| Default
| Meaning

| `<rootDir>`
| required
| Queue directory, or a directory containing queue directories.

| `--keep N`
| `2`
| Retain at least the last `N` roll-cycle numbers. Size this for late-arriving readers, not just recent files - see <<sizing-keep>>.

| `--min-free size`
| `10G`
| Warn if usable disk falls below this size on any distinct filesystem holding the root or a queue directory (queues may be symlinks or mounts onto other filesystems). Uses Chronicle size parsing, e.g. `500M`, `10G`, `2T`.

| `--delete`
| off
| Actually delete removable files. Without this, the tool is a dry run. Cannot be combined with `--park`.

| `--park name,...`
| none
| One-shot: retire named tailers by setting their committed index to `0`, then report the resulting analysis without deleting. Cannot be combined with `--delete` or `--interval` - park first, then sweep with `--delete` separately. Replicated named tailers (ids starting `replicated:`) are refused with a warning, to avoid desynchronising replication; a name found in no queue also warns.

| `--interval secs`
| off
| Repeat the sweep every `secs`; fractional seconds are accepted (a value that rounds to under a millisecond runs a single sweep). Without this, the tool runs once. Cannot be combined with `--park`.

| `--fail-on-warn`
| off
| Exit with code `3` if the sweep emits any retention warning: a lagging tailer, low disk, a failed delete, a skipped (unopenable) queue, a nested queue directory, a root that contains no queues, an unknown `--park` name, or a refused replicated-tailer park.

| `--verbose`, `-v`
| off
| Emit a detailed per-queue trace at debug level. See <<Logging and exit behaviour>> for enabling debug output.
|===

== Dry run first

The default mode does not delete files.

[source,bash]
----
mvn exec:java@RollFileCleanup -Dexec.args="/var/queues --keep 48 --min-free 20G --verbose"
----

This reports the files that would be removable, and any lagging tailers, without changing anything. Because parking changes what a later delete pass will remove, `--park` is a separate one-shot step (see <<Parking a dead named tailer>>): the dry run and the delete pass then analyse the same tailer positions, so the preview matches what `--delete` will actually do.

NOTE: The removable list and the per-queue summary are emitted at debug level. Enable debug logging (see <<Logging and exit behaviour>>) to see them; otherwise a clean dry run prints only warnings.

== Deleting files

Once the dry run is understood, add `--delete`:

[source,bash]
----
mvn exec:java@RollFileCleanup -Dexec.args="/var/queues --keep 48 --min-free 20G --delete --fail-on-warn"
----

Deletion happens after the queue has been closed and any pending store releases have completed, so no file is deleted while still memory-mapped by the sweep (a mapped file cannot be deleted on Windows, and its space is not reclaimed until unmapped on Linux). Deletion stops on the first failed file in a queue; later candidates are left untouched because ordering matters, and the warning includes the reason the delete failed. A failed delete is a warning, so under `--fail-on-warn` it makes the sweep exit `3` rather than reporting success while disk was not reclaimed - which is what you want when a permission or lock problem is blocking cleanup.

== Parking a dead named tailer

A dead named tailer can pin old roll files indefinitely. Parking resets its committed index to `0` so it no longer pins retention.

Parking irreversibly discards that consumer's committed position, so it is a deliberate, one-shot action, run on its own:

[source,bash]
----
mvn exec:java@RollFileCleanup -Dexec.args="/var/queues --keep 48 --park old-gateway --fail-on-warn"
----

It cannot be combined with `--delete` or `--interval`. Bundled with `--delete`, parking would silently widen the delete pass beyond what a dry run previewed; repeated by an interval loop, it would re-reset a consumer that has since been restarted, discarding its progress every sweep. Park once, review the reported analysis, then sweep with `--delete` separately.

A `--park` name that matches no named tailer in any queue is warned about rather than silently ignored - otherwise a typo would leave the operator believing a tailer was retired while its stale index continues to pin rolls.

If a parked consumer is restarted later, it resumes from the oldest roll still available. It loses only the data that retention has since removed, not the whole queue.

Parking a replicated named tailer (an id starting `replicated:`) is refused: the tool warns and changes nothing. A replicated tailer's position is coordinated with its sinks through version metadata, and resetting it here without bumping that version could desynchronise replication. Retire a replicated consumer through replication configuration, not this tool.

== Logging and exit behaviour

Warnings are emitted through `Jvm.warn()`:

* named tailers pinning rolls below the keep floor;
* free disk below `--min-free` on any filesystem holding the root or a queue;
* a failed file delete (with the reason);
* a queue that could not be opened or analysed (skipped; the sweep continues);
* a directory that contains no queues;
* a nested queue directory inside a queue;
* a `--park` name found in no queue;
* a refused `--park` of a replicated named tailer.

Operational trace and positive status are emitted through `Jvm.debug()`:

* per-queue summary;
* `RETENTION_OK`;
* `RETENTION_PARKED`;
* per-tailer verbose trace.

[IMPORTANT]
====
Only `Jvm.warn()` output is visible by default. Everything in the `Jvm.debug()` list above - including the removable summary a dry run produces and the whole `--verbose` trace - is at debug level, so an unconfigured run prints nothing beyond warnings. To see it, enable debug logging, for example:

[source,bash]
----
mvn exec:java@RollFileCleanup \
  -Dorg.slf4j.simpleLogger.defaultLogLevel=debug \
  -Dexec.args="/var/queues --keep 48 --verbose"
----

or set the equivalent `DEBUG` level for `net.openhft.chronicle.queue.internal.main.InternalRollFileCleanupMain` in your logging backend.
====

Exit codes from `main()`:

[cols="1,4", options="header"]
|===
| Code | Meaning

| `0` | Success (or a warning fired without `--fail-on-warn`).
| `1` | Usage error: missing `<rootDir>`, an unknown option, a missing or malformed option value, `--keep` below 1, or `--park` combined with `--delete`/`--interval`. No metadata is changed and nothing is deleted.
| `2` | The root is not an existing directory.
| `3` | A retention warning fired and `--fail-on-warn` was set, so a cron job or scheduler fails loudly instead of silently doing nothing.
|===

== API entry points

The tool is built on a small API that can be used directly:

[source,java]
----
List<File> removable = FileUtil
        .removableRollFileCandidatesByTailerPosition(queueDir, 48)
        .collect(Collectors.toList());
----

For lower-level diagnostics:

[source,java]
----
NavigableMap<String, Long> indexes = queue.namedTailerIndexes();
boolean parked = queue.parkNamedTailer("old-gateway");
File rollFile = queue.fileForCycle(cycle);
----

== Operational checklist

Before running with `--delete`:

* run the command without `--delete`;
* check the named tailers reported as lagging;
* decide whether each lagging tailer is live, dead, or intentionally paused;
* park only named tailers you are prepared to retire;
* keep enough cycles to cover normal outage, restart time, and any consumer that may arrive or replay later (see <<sizing-keep>>);
* use `--fail-on-warn` from automation if lag or low disk should fail the job.

The point is not to be clever. It is to make an offline clean-up predictable enough that you can run it in production without guessing.
