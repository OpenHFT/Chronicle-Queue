= Index Spacing
keywords: index sizing, chronicle queue, queue, java
author: Julia Gustafsson
:reftext: Index sizing
:navtitle: Index sizing
:source-highlighter: highlight.js

Each queue explicitly indexes certain excerpts with a fixed interval for quicker referencing.
What excerpts are indexed is controlled with the parameter `indexSpacing(int spacing)`, a property that defines the space between indexed excerpts.
In the extreme case of setting this property to 1, every excerpt is indexed.

The natural trade-off associated with this value is that more frequent indexing yields faster random access read, but decreases the sequential write performance.
However, the sequential read performance is not affected by this property at all.

The index spacing can be set when building your Chronicle queue as follows:

[source,java]
----
SingleChronicleQueue queue = ChronicleQueue.singleBuilder("queue")
    .indexSpacing(16)
    .build();
----

The default index spacing varies depending on the xref:roll-cycle.adoc[roll cycle], per the table below.

|===
| Roll-cycle | Default index spacing
| `SMALL_DAILY` | 8
| `MINUTELY`, `HOURLY`  | 16
| `DAILY`, `LARGE_HOURLY` | 64
| `LARGE_DAILY` | 128
| `XLARGE_DAILY`, `FAST_DAILY`, `WEEKLY`, `SIX_HOURLY`, `FOUR_HOURLY`, `TWO_HOURLY`, `FAST_HOURLY`, `HALF_HOURLY`, `TWENTY_MINUTELY`, `TEN_MINUTELY`, `FIVE_MINUTELY` | 256
| `HUGE_DAILY`, `LARGE_HOURLY_SPARSE` | 1024
| `LARGE_HOURLY_XSPARSE`, `HUGE_DAILY_XSPARSE` | 1048576
|===

TIP: For more information about queue indexing, see xref:queue-operations:indexing.adoc[Indexing].

== Warming indexing code

Call the utility before latency-sensitive work:

[source,java]
----
net.openhft.chronicle.queue.util.ToolsUtil.warmup();
----

The first caller performs 64,000 verified writes and reads on a private temporary queue with index spacing 4, index count 4096 and a 4 MiB block size.
This exercises indexed and non-indexed appends, index-array transitions and indexed seeks.
A lazy static initializer runs the work once per defining classloader; repeated calls do no further work and concurrent callers wait until cleanup finishes.
Ordinary use of other `ToolsUtil` methods does not trigger it.

Configure a writable `java.io.tmpdir` with suitable scratch storage before calling; the utility closes and deletes its own queue and never touches an application queue.
Ordinary initialization or cleanup failure is reported as `IllegalStateException` on each call without retrying.
Work is finite, but filesystem operations have no hard elapsed-time bound.

This exercises shared code and encourages compilation; it cannot guarantee a JIT tier, zero allocation or page residency for application queues.
Index cursors belong to individual threads and stores and may be reclaimed after GC; a new roll also creates a new store.
Warm and measure each application's threads and stores separately, including after GC and rolls where relevant.
The utility does not call `System.gc()`, change global logging handlers or alter affinity.
